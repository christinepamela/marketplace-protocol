### B25 — enforce `expires_at` on the opportunities query — ✅ DONE
**What:** the provider-facing `/logistics/opportunities` handler now hides RFQs whose `expires_at`
has passed.
**Why it mattered:** `expires_at` was written by both quote-request paths and read by nothing. An
RFQ that expired on 2026-08-01 was still being served on 2026-08-14. After the two-month gap, **all
eight open RFQs were expired** and the provider pool still showed six of them.
**How:** one added filter in the query, directly under the existing `.or()` at ~line 657:
```ts
.or(`expires_at.is.null,expires_at.gt.${new Date().toISOString()}`)
```
Design decisions, so they are not re-litigated:
- **In the query, not after it.** The query is `.limit(50)`; filtering afterwards would let dead
  rows crowd live ones out of the 50.
- **A null `expires_at` is kept**, not dropped — a legacy row with no expiry should not vanish
  silently. Every row written since S30 has one.
- **Read-time filtering, not a scheduled job.** A job has something to fail silently; a filter does
  not. Expired rows keep `status = 'open'` in the database.
- **Three other `quote_requests` readers were reviewed and deliberately left alone:** the
  accept-quote ownership check (~541) and the seller's per-product history (~859) *should* still see
  expired rows; the buyer pending endpoint (~1042) is the open item below.

**Files changed:** `src/api/routes/logistics.routes.ts`, +5 lines (1400 → 1405 by `find /c /v ""`).
Server-side only — no SDK change, no rebuild.

### The BitHaul finding — ✅ DONE (diagnosis and doc corrections; no code)
**What was found:** the S40 handover, B20, B21, D21, T18 and the `OPERATIONS.md` fixture note all
treated BitHaul as a provider with no capability data that "bypasses the filter". That is wrong.

**How it surfaced.** The B25 baseline showed BitHaul seeing **6 of 8** open RFQs. If BitHaul really
bypassed the filter it would have seen all 8. Two were missing:

| Missing RFQ | Route | Why withheld |
|---|---|---|
| `c5d3f94c` | MY→**MY** | names a destination; BitHaul's only route is MY→SG |
| `d4cc2d30` | MY→**DE** | same |

**Evidence — BitHaul's row, queried 2026-10-21:**

| Field | Value |
|---|---|
| `routes` | `[{origin MY, destination SG}]` |
| `incoterms_supported` | `["DAP","DDP"]` |
| `modes` | `[]` |
| `weight_min_kg` / `weight_max_kg` | null / null |
| `door_pickup` / `door_delivery` | false / false |
| `service_regions` | MY, SG, DE, GB, US, CA, NL, FR |

**D21's own first line already said so.** It records "BitHaul's route MY→SG" from S32. S40 reopened
it without re-reading it and without querying the row. D21's S34 test — a null-destination RFQ from
MY reaching a provider whose only route is MY→SG — was the *correct* test. **The reopening is
withdrawn.**

**How BitHaul got its capabilities — checked against the code, not assumed:**
- The registration insert writes exactly five fields: `business_name`, `identity_did`,
  `service_regions`, `shipping_methods`, `insurance_available`.
- The logistics-marketplace registration form has no routes, incoterm, weight or door inputs.
- Nothing in `logistics.routes.ts` ever writes `routes` or `incoterms_supported`.

So BitHaul's routes and incoterms were set by hand, almost certainly in SQL. **B21 stands exactly as
written.** When it happened is unknowable — there is no `updated_at` (D47).

**What this changes:**
- **B20 is narrower than logged.** The pool filters correctly for providers that have capability
  data (BitHaul, SatsFleet) and not at all for freshly registered ones. Behaviour differs by
  provider, which is arguably harder to diagnose than uniform breakage.
- **B22 is now observed, not predicted.** BitHaul's `service_regions` lists DE; its `routes` does
  not. The matcher withheld a MY→DE RFQ from it while a `searchProviders` browse would have listed
  it as serving DE. Seller sees one list, matcher uses another.
- **The fixture-cleanup plan shrinks.** BitHaul already has MY→SG, DAP/DDP and no door pickup. It
  needs only `modes` (`sea_lcl`) and weight bounds (0.5–30 kg).
- **The case for building the two-door UI after B20/B21/B22 weakens** — see Open decision 1.

**Process lesson, recorded because it is the second occurrence.** S40 struck architectural
principle 9 by checking against an older document (S37). It then reopened D21 against its own
