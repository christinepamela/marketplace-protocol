## Architectural Principles (Always-On)

1. Protocol is passive infrastructure — 0.5%+0.5% from payouts at escrow release, never added to buyer's total.
2. Federation is the goal from day one.
3. Cryptographic identity (secp256k1) — protocol never holds passwords/keys/KYC docs.
4. Nostr is plumbing, Rangkai owns UX and search.
5. Small business first — hide complexity. If something seems hard, check for the simpler framing first.
6. Bitcoin is the invisible rail — v1 pays out BTC/USD directly, invisible conversion is v1.5 (R11).
7. Terminology: seller, buyer, logistics — not vendor, provider, courier.
8. No centralized consolidation hubs — logistics stays inside the decentralized pool. Consolidation is a matching problem for the pool, not infrastructure Rangkai owns. (S33, R23)

### D31 — KYC gate on "I'll arrange my own logistics" — ✅ FIXED

The S32-shipped checkbox let any buyer (KYC or not) skip the logistics pool entirely. Fixed S34:

- **Non-KYC buyers:** tick the checkbox → self-arrange flow ends there, `ownLogistics: true` passed to order creation. No pool involvement.

The `kycLogisticsReady()` function in `checkout/page.tsx` handles the gate logic.

### L15c — Buyer-initiated RFQ broadcast — ✅ DONE, TESTED, PUSHED

**What was built:**

- New backend endpoint `POST /api/v1/logistics/quote-requests/buyer` — reads product logistics data server-side, destination from buyer's shipping address, verifies caller is not the product's seller.
- New backend endpoint `GET /api/v1/logistics/quote-requests/buyer/pending` — returns open requests with pending quotes. Initially had a Supabase nested join bug (500 on the ambiguous FK between `quote_requests` and `shipping_quotes` via `product_id`); fixed S34 by splitting into two sequential queries.
- Two new SDK methods: `requestQuoteAsBuyer()`, `getBuyerPendingQuoteRequests()`.
- New file `rangkai-marketplace/lib/api/logistics.ts` — buyer-facing API wrappers.
- `createOrdersFromCart()` now accepts `acceptedLogisticsQuotes` per vendor — closes the L15a known gap.
- Checkout polls every 10 seconds, manual refresh available. Quote accept button transitions checkout to confirmed state.

**Fixes made during L15c testing:**
- `quote.service.ts` `acceptQuote()` — the "already accepted" guard was blocking buyer RFQ accepts because the product already had a seller's standing accepted quote. Fixed by checking context: if a `quote_requests` row exists where `requester_did` is not the product's vendor, skip the guard (buyer RFQ context). Seller-context still enforces one accepted quote per product. See D35 for the real schema-level fix.
- `logistics.routes.ts` `POST /quotes/:id/accept` ownership check updated to also allow the RFQ requester (buyer) to accept, not just the product owner.

**Confirmed live:** DB row — Bitty Buy broadcast, BitHaul submitted quote, Bitty Buy accepted, "Shipping confirmed — $8.00 · included in your order total" displayed. Order summary showed correct total.

**D35 logged:** Buyer RFQ accepted quotes and seller standing accepted quotes now coexist on the same product with no schema-level distinction. `getAcceptedShippingQuote()` picks the newest, which can be the buyer's quote, causing wrong price to show for other buyers. Real fix: add `context` column to `shipping_quotes`. Also: abandoned checkout leaves open `quote_requests` rows that show stale state on next visit. Both tracked in D35.

### B5 — Wrong provider loading in logistics-marketplace — ✅ FIXED

Root cause: `ProviderContext` called `searchProviders({ identity_did: did })` but `identity_did` is not a supported filter in the backend schema — silently ignored, returned all providers, picked `[0]` (SatsFleet Express). Fixed by client-side `.find(p => p.identity_did === did)` after fetching all. Real fix (GET /logistics/providers/me) tracked in D34.
