### Fix 1 — dead `requireLogisticsQuote` reference removed — ✅ DONE S40

**What was fixed:** S39 derived `require_logistics_quote` from incoterm server-side and removed the form field, but left `requireLogisticsQuote: formData.requireLogisticsQuote` in the `productData` object. The `FormData` type has no such field.
**Why it mattered:** Runtime was unaffected (evaluated `undefined`, dropped from JSON, server derived its own value) but `tsc --noEmit` failed on it. The S39 build was only green because Next dev transpiles via SWC without typechecking — which is how B23 was found.
**Files changed:** `rangkai-marketplace/components/vendor/ProductForm.tsx`

### Fix 2 — RFQ broadcast moved to AFTER the publish gate — ✅ DONE S40

**What was fixed:** The L12 broadcast fired *before* the R21 activation call. On a blocked publish — DAP/DDP with no accepted standing quote, which is exactly the path R21 was built for — the RFQ had **already gone to the pool for a product that stayed a draft**. Providers could quote something buyers could not see.
**How:** Block relocated after the activation block, guarded by `!activationError`. Note that guard only bites in create mode; in edit mode a gate rejection throws out of `sdk.catalog.update` into the outer catch and never reaches the broadcast. Commented in place.
**Execution order in `handleSubmit` is now:** seller estimate (D24) → publish gate (R21) → RFQ broadcast (L12) → alerts.
**Files changed:** `ProductForm.tsx`

### Fix 3 — edits only re-broadcast when a logistics-material field changed — ✅ DONE S40

**What was fixed:** The broadcast condition checked `saveAs === 'active'` but not `mode`. Every edit-and-publish of an active product inserted a fresh `quote_requests` row — a third call site nobody had counted.
**Pam's call, and it was the right one:** colour and description don't change the shipping job; weight, dimensions, units, MOQ, origin country, incoterm and HS code do. Restricting to create-mode-only would have meant a corrected weight never reaching providers.
**How:** New `logisticsMaterialFieldsChanged()` helper does a shallow compare of exactly those fields against the loaded `product` prop.
**Files changed:** `ProductForm.tsx`

### Fix 4 — unit conversion at the RFQ boundary — ✅ DONE S40

**What was fixed:** The form offers kg/lb/g and cm/in. The broadcast sent the raw number as `weight_kg` and raw dimensions as `dimensions_cm` with no conversion — a seller picking lb sent "3" as three kilograms.
**How:** New `toKg()` / `toCm()` helpers, rounded to 2dp and 1dp to match existing column precision.
**Still open:** the product record deliberately stores the seller's chosen unit for display, so **any other consumer of `product.logistics` has the same latent bug.** The buyer-side RFQ path from L15 is the obvious candidate — check it, don't assume.
**Files changed:** `ProductForm.tsx`

## Critical finding — the RFQ matcher does nothing in production

Found by reading `logistics.routes.ts` 629–710 (the `/opportunities` handler) against the registration schema at 37–38. Two facts combine badly:

1. **Registration collects no capability data.** The Zod schema requires only `service_regions` and `shipping_methods`; it never collects `routes`, `modes`, `incoterms_supported`, the door flags or the weight bounds. Every self-registered provider is blank. BitHaul isn't a stale row — it's what registration produces today.
2. **The matcher treats blank as "match everything."** `hasRoutes` and `hasIncoterms` are graceful-degradation guards; empty means the filter is skipped entirely.

Together: **every real provider sees every RFQ and the filter is inert.** The incentive is inverted — a provider who declares its capabilities is the only kind that can be filtered *out*. SatsFleet, the only properly configured provider, is the only one that can miss an opportunity.

Weight has no degradation guard at all — the bounds apply unconditionally when non-null. SatsFleet's 0.1 kg floor silently drops any RFQ where weight arrived as 0, which is exactly what Fix 4's bug and D46's gap were producing.

**This invalidates D21's S34 confirmation.** D21 was closed because BitHaul saw Bitshop's null-destination broadcasts. BitHaul saw them because it bypasses the filter, not because origin-only matching works. Re-confirm against SatsFleet via curl.

Logged as **B20** (matcher), **B21** (registration), **B22** (two vocabularies). D21 reopened.

## Design decisions taken S40

### Auto-broadcast stays default, with seller control added — see D44

Pam's reasoning, recorded so it isn't re-litigated: auto-broadcast on publish stays, because logistics deserves the chance to pitch and the seller has final say on who ships. But the seller must also be able to not broadcast at all, browse the pool, and approach a specific provider directly — including one they already work with who has signed up.

Framing correction that settled the debate: **auto-fire was already the status quo.** "Manual-only" would have meant *removing* working L12 behaviour, not declining to add something. Also revised during the session: the empty-pool argument for a manual button is weak — an RFQ into an empty pool costs nothing. The button's real value is control and sequencing, which survives once the pool fills.

### RFQ payload — MOQ is the biggest gap — see D46

Logistics quotes a shipment, not a unit. `formData.pricing.moq` already exists in the form and simply isn't forwarded. Volumetric weight is why it matters: on the real product row (0.7 kg, 30×20×20 cm, MOQ 35), actual is 24.5 kg but volumetric at /5000 is **84 kg** — 3.4× — and we currently broadcast the 0.7. **Do not build a packing optimiser**; collect the carton spec the seller already has and compute chargeable weight from it. Full reasoning in D46.

### Logistics do need Incoterms — see D47

Incoterm defines where the logistics job starts and stops and who clears customs. DDP means the carrier clears import customs and fronts duty; DAP means they stop at the door with duty unpaid; FOB means origin-side only. Same two cities, three different jobs, three prices. What's wrong is the *presentation* — ask it in operator language, not as a bare Incoterm multi-select.

### Provider fixture cleanup — designed, NOT executed

Set the two providers deliberately different so a capability filter is provably working rather than provably rendering:
- **SatsFleet** — full service: `air_express` + `air_freight` + `sea_lcl`, door pickup and delivery, DAP/DDP/FOB, wide routes, 0.1–500 kg.
- **BitHaul** — deliberately narrow: `sea_lcl` only, no door pickup, DAP/DDP only, MY→SG only, 0.5–30 kg.

Then a 24.5 kg / 0.42 CBM footwear RFQ matches both; a 300 kg one matches only SatsFleet; an FOB one matches only SatsFleet.

**Critical: BitHaul must be given explicit narrow capabilities, not left empty.** Per B20's degradation guards, empty doesn't test the filter — it bypasses it. **Do not run the cleanup until B22 resolves which field pair is authoritative.**
