## Architectural Principles (Always-On)

1. Protocol is passive infrastructure — 0.5%+0.5% from payouts at escrow release, never added to buyer's total.
2. Federation is the goal from day one.
3. Cryptographic identity (secp256k1) — protocol never holds passwords/keys/KYC docs.
4. Nostr is plumbing, Rangkai owns UX and search.
5. Small business first — hide complexity. If something seems hard, check for the simpler framing first.
6. Bitcoin is the invisible rail — v1 pays out BTC/USD directly, invisible conversion is v1.5 (R11).
7. Terminology: seller, buyer, logistics — not vendor, provider, courier.
8. No centralized consolidation hubs — logistics stays inside the decentralized pool.
9. **NEW (S39, R21):** protocol owns rules and data; each marketplace owns the words. Enforcement (like the publish gate) lives server-side at the protocol, never in UI copy — every marketplace inherits it for free (R20 in practice).

### R21 core — incoterm-aware hard publish gate — ✅ DONE S39

**Design decisions confirmed with Pam (all settled before coding):**
- **The gate is Incoterm-aware**, replacing the Incoterm-blind S30 rule. DAP/DDP (seller arranges main freight): publish requires ≥1 accepted `seller_standing` quote — a provider firm quote OR the seller's own estimate (D24). EXW/FOB (buyer arranges main freight): exempt, nothing to quote. The exempt cases route naturally into the L15c/L15d buyer pool flows.
- **Anon sellers exempt** (no pool access). Gate keys on JWT `req.user.type === 'kyc'`.
- **Transition-only enforcement (grandfathering option 1):** checked only when status moves to `active` from anything else. Already-active products untouched; deactivating is never gated. Test data cleanup at launch makes retroactive enforcement unnecessary.
- **`require_logistics_quote` is now DERIVED from the Incoterm** (DAP/DDP → true), never seller-toggled. The manual checkbox is gone from the form and the field is removed from both API Zod schemas (Zod silently strips it from any old client). The column stays — L11's checkout gate reads it unchanged. Rationale: Incoterm and "should seller arrange shipping" are the same question in two languages; two controls could contradict each other.
- **Incoterm IS the seller's per-listing choice.** Seller default (DAP), seller per-listing choice via Incoterm, buyer override at checkout (L15c/d) — all three of Pam's requirements with no new toggle.
- Four v1 Incoterms only (EXW/FOB/DAP/DDP). No expansion to all 11 yet.

**Discovery en route — the Publish button never published:** `createProduct()` hardcodes `status:'draft'` and the create schema strips `status`, so every UI "Publish" actually created a draft; Pam had been activating via the eye-icon toggle on My Products (which PUTs `{status}`). This became the foundation rather than a bug: PUT is the ONLY road to `active`, so a single gate at PUT covers the form's Publish, the eye icon, and raw API calls alike. The form now performs the real flow: create (draft) → submit estimate → gated activation → honest alert per outcome.

**What was built:**
1. **Migration (Supabase SQL, applied, snippet saved):** `UPDATE products SET require_logistics_quote = (incoterm IN ('DAP','DDP'));` — all 4 then-existing products flipped to true; all had accepted quotes so L11's checkout gate was unaffected.
2. **`catalog.routes.ts`:** `requireLogisticsQuote` deleted from create + update schemas. PUT handler derives it whenever `incoterm` is in the body. **The gate** sits in the PUT handler before `updateProduct()`: on transition to `active`, if seller is KYC and effective incoterm (incoming ?? stored ?? 'DAP') is DAP/DDP, query `shipping_quotes` for an accepted `seller_standing` row on the product; none found → `ValidationError`: *"This product is sold \<INCOTERM\>, which means you arrange the shipping — it needs a shipping quote before it can go live. Add your own shipping estimate or accept a logistics provider's quote, then publish."* Route-level throw → clean HTTP 400 (D39's 500-masking never touches this).
3. **`product.service.ts`:** `createProduct()` derives `requireLogisticsQuote` from the incoterm and ignores any request value.
4. **`ProductForm.tsx`:** publish sequencing rewritten — estimate is submitted BEFORE the activation call so the gate can see it; activation is `sdk.catalog.update(id, {status:'active'})`; on gate rejection the product stays a draft and the alert carries the server's reason. Client-side pre-check blocks Publish in create mode (KYC + DAP/DDP + empty estimate) with a clear message before the server is ever hit. Estimate block renders for DAP/DDP only; EXW/FOB get an info note ("the buyer arranges the main freight — no shipping quote is needed to publish"). The L12 RFQ broadcast is skipped for EXW/FOB.
5. **`app/vendor/products/page.tsx`:** `handleToggleStatus` now surfaces the server's actual error message in the alert (previously a generic "Failed to update product status" swallow) — so the eye-icon path shows the gate's reason verbatim.

## Troubleshooting Reference

### Health endpoint says healthy but nothing works
Health check doesn't touch the DB. If the API terminal shows `[Scheduler] ... TypeError: fetch failed`, Supabase is paused — restore at supabase.com/dashboard. Confirm real DB connectivity with a login curl, not /health.

### Activating a product returns 400 "This product is sold DAP/DDP … it needs a shipping quote before it can go live"
R21's gate, working as designed. Satisfy it with a seller estimate (`POST /logistics/quotes/seller-estimate`, owner-only) or by accepting a provider quote on the product's Quotes page, then re-activate. EXW/FOB products and anon sellers are never gated.

### Product created via API/form is always `draft`
By design — `createProduct()` forces draft and the create schema strips `status`. Activation is a separate PUT `{status:'active'}` (gated per above). The form does this automatically on Publish since S39.

### `requireLogisticsQuote` sent to the API is silently ignored
By design since S39 — derived from the Incoterm (DAP/DDP → true) at create and on any incoterm change. Zod strips the field from requests. Not a bug.

### Eye-icon "Activate" on My Products shows a long error message
That's the server's gate reason, surfaced on purpose since S39 (previously swallowed behind a generic message).

### Seller-estimate endpoint returns "already has a seller estimate" / "already has an accepted provider quote"
Working as designed — one accepted standing quote per product (D29 index enforces at schema level too). To replace an estimate: accept a real provider quote (auto-supersedes). No edit-estimate path in v1.

### Product page shows no shipping block despite a known accepted quote
Check the quote's `context` — if `buyer_rfq`, display correctly ignores it. If a quote that *should* be `seller_standing` is stamped `buyer_rfq`, that's D40 (context inference bug). Repair by hand: `UPDATE shipping_quotes SET context = 'seller_standing' WHERE id = '<id>';`

### Deleting test shipping_quotes fails with FK error on orders
`orders.logistics_quote_id` references quotes. Exclude them:
```sql
AND id NOT IN (SELECT logistics_quote_id FROM orders WHERE logistics_quote_id IS NOT NULL)
```

### Provider quote shows "(estimated)" unexpectedly
Its `valid_until` passed — L14's designed firm→estimated conversion, not a bug (and not a seller estimate; those say "Seller's estimate"). D23 (seller notification at conversion) is still open.

### "getIdentity is not a function" in browser console on product pages
B17, known, graceful. S40 priority #2.

### SDK changes not taking effect
`cd packages\sdk && npm run build`. Verify junction: `dir node_modules\@rangkai` should show `<JUNCTION>`.
